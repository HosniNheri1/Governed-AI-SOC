01 — Overview

Detection, then automated response, then governing the AI that does the detecting

The question: does an ML detector add value over Suricata rules alone for detecting scans and brute force in a small network, and how can it be governed? The hypothesis and the metrics were written down before any result. The answer is a measured one, with its limits stated next to it.

📉 Rules alone missed 10 of 24

Suricata flagged 14 of 24 attack sessions (recall 0.583). The Random Forest flagged all 24, and the hybrid (Suricata OR model) matched it, with 0 false positives on 8 benign sessions.

🧱 A gain over four local rules

The baseline is Suricata alerts from SIDs 9000001 to 9000004, not a tuned ruleset. A stronger baseline could close much of the gap.

⚠️ A perfect score is a warning

24 detections out of 24 only support a recall of at least 0.883 (one-sided 95% bound). 0 false positives out of 8 allow a rate up to 0.312.

🧭 Governance found real gaps

The recorded analyst decision is a fixed value in the exported workflow, and a declined alert ends as ABORTED with no recorded reason. Both are in the risk register.

02 — Scope & Architecture

An isolated lab, a defined scope, no certification claim

All attacks (Nmap SYN scans, Hydra brute force on SSH, FTP and HTTP) ran only inside an isolated lab on a private network (172.30.0.0/24), against hosts I own. No production data and no personal data were used. This project is implemented on a defined scope; it is not certified. Out of scope: production traffic, real blocking, full Annex A coverage, adversarial-ML experiments beyond a documented risk entry.

03 — Method

Fixed before seeing results, evaluated by session

The research design (question, hypothesis H1, decision rule, threats to validity) is committed in docs/01-research-design.md. The decision rule: the hybrid is useful if it improves recall on at least one attack class over Suricata alone, while keeping the false-positive rate within one percentage point.

ClassSessionsDescription
benign8Normal logins, web requests and transfers, including some failed logins
ssh_bruteforce7Hydra against SSH
nmap_syn_scan6Nmap SYN scans
ftp_bruteforce6Hydra against FTP
http_bruteforce5Hydra against the HTTP login form

Data

32 sessions collected on 2026-11-07. Labels come from my own attack run log, by time window and source IP.

Features

20 numeric features per session: volume, timing, flow bytes and packets, TCP flags, protocol counters. No IP address or user identifier is a feature.

Model

Random Forest, 200 trees, balanced class weights, fixed seed 42.

Evaluation

5-fold stratified cross-validation by session, one out-of-fold prediction per session. Suricata alone, model alone, hybrid OR and hybrid AND on the same sessions.

Multiclass accuracy is 31/32 = 0.969. The one error is an nmap_syn_scan session predicted as http_bruteforce; it still counts as an attack in the binary table.

Decision rule met — recall improves on every attack class over Suricata alone, with the same false-positive rate. That supports H1 for this lab and these four rules. It does not show that the model replaces Suricata, and it does not show production performance.
Read the perfect score with care — protocol counters such as n_ftp_events, n_ssh_events and n_http_post may reveal the attack type directly. The evaluation script now also computes a reserved test split, repeated splits and an ablation without these counters.

07 — Limits & Incidents

What this does not show, and what actually broke

Small, synthetic, single-lab data. 32 sessions collected on one day, with labels derived from my own attack scripts. Results do not transfer directly to production.
Unit of analysis. The evaluation unit is the session, not the 60-second window fixed in the research design. The deviation is recorded in the model card and the risk register.
Unmeasured gap. No slow scan or low-and-slow brute force was collected, so that expected gap is unmeasured, not absent.
Silent telemetry loss. The Suricata and victim containers stopped between sessions, so ingestion into Splunk was about three days stale when the alert was next tested. The monitoring plan now has an ingestion-freshness alert and a restart checklist.
Credential hygiene. A workflow export contained a clear-text API key and password. Credentials were rotated, the export was masked and the repository history was scanned before publication.
